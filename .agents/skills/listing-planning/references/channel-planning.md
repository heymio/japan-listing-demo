# Channel planning and frontend reference intake

## Platform Capability versus Frontend Visual evidence

Keep these separate:

- **Platform Capability** — editable fields/regions, account access, current module/component families, limits, policies, ownership, publishing workflow, and mobile constraints.
- **Frontend Visual evidence** — current consumer-facing page captures showing shell anatomy, section order, controls, interaction, responsive behavior, and brand/platform ownership boundaries.

Official rules do not substitute for current frontend visual evidence.

## Primary Reference

When a channel-native demo is planned, ask once whether the user has a current preferred Reference URL, ASIN, retailer/store page, screenshot set, or approved frontend capture.

A valid supplied reference becomes the candidate **Primary Reference** unless it is inaccessible, stale, materially different from the requested page type, or otherwise unsuitable. If none is supplied, research 1–3 current comparable consumer-facing references and recommend one.

## Planning outputs

Capture only what Planning needs to design the page:

- current editable/brand-controlled regions;
- platform-controlled boundaries;
- current module families and limits;
- desktop/mobile structure where material;
- interaction patterns relevant to planned content;
- Primary Reference and any explicitly scoped secondary reference;
- open capability/frontend questions.

## Ownership

Competitor pages can evidence competitor execution and frontend presentation. They do not prove account access for the current project.

## Handoff

Planning should pass resolved channel structure, ownership, module constraints, and Primary Reference identifiers into the Production Handoff. Final implementation fidelity belongs to the later hardening plane.
